## 문서용 workflow.md 템플릿

문서용 프로젝트의 workflow.md를 생성할 때 이 템플릿을 기반으로 한다.

```markdown
---
title: {Project Name} Workflow
description: 문서 작성 워크플로우
type: workflow
created: {YYYY-MM-DD}
---

# Documentation Workflow

1. 계획 수립
2. 계획 검토
3. 초안 작성
4. 초안이 목적에 부합하는지 검토
5. 구조와 가독성 검토
6. AI-Friendly 규칙 준수 여부 검토
7. 기존 문서와 중복/모순 여부 검토
8. 참조 링크 및 파일 경로 검토
9. 전체 변경 사항 재검토
10. 불필요해진 문서 정리
11. 최종 품질 검토
12. 독자 흐름에서 문제가 없는지 확인
13. 배포 가능 퀄리티인지 검토
14. 커밋 및 PR 작성

## 1. 계획 수립

문서의 목적과 범위를 정한다.
- 대상 독자를 명확히 한다
- 문서가 어떤 질문에 답하는지 정의한다
- 계획은 docs/plan/{순번}-{날짜}-{계획서명}/plan.md 에 작성한다
  - plan.md는 계획서의 핵심 요약이며, 상세 내용은 같은 디렉토리의 개별 문서를 참고하라고 가이드한다
  - 상세 문서는 {순번}-{상세내용}.md 형식으로 필요한 만큼 작성한다

## 2. 계획 검토

수립한 계획이 적절한지 검토한다.
- 문서의 목적과 범위가 명확한지 확인한다
- 대상 독자 수준에 맞는 깊이인지 확인한다
- plan.md의 핵심 요약이 상세 문서들과 일치하는지 확인한다
- 상세 문서 간 내용이 중복되거나 모순되지 않는지 확인한다

## 3. 초안 작성

계획에 따라 문서를 작성한다.
- 검색 관련 스킬이 있다면 활용한다
- frontmatter를 먼저 작성한다
- 각 섹션 첫 줄에 1문장 요약을 둔다
- 한 문서는 하나의 주제만 다룬다

## 4. 초안이 목적에 부합하는지 검토

작성한 문서가 원래 계획을 충족하는지 확인한다.
- 정의한 질문에 모두 답하고 있는지 확인한다
- 대상 독자가 이해할 수 있는 수준인지 확인한다
- 범위를 벗어난 내용이 포함되지 않았는지 확인한다

## 5. 구조와 가독성 검토

문서의 구조가 읽기 쉬운지 점검한다.
- 제목 계층이 `#` ~ `###` 범위 내인지 확인한다
- 300줄을 넘지 않는지 확인한다. 넘으면 분리한다
- 순서가 있는 내용은 숫자 목록, 없으면 `-` 를 사용했는지 확인한다

## 6. AI-Friendly 규칙 준수 여부 검토

docs/guide.md의 AI-Friendly Writing Rules를 따르는지 확인한다.
- 모호한 표현 없이 구체적으로 작성했는지 확인한다
- 지시 대명사("이것", "그것") 대신 대상을 직접 명시했는지 확인한다
- 동일한 개념에 동일한 용어를 사용했는지 확인한다

## 7. 기존 문서와 중복/모순 여부 검토

프로젝트 내 다른 문서와의 관계를 점검한다.
- 이미 같은 내용을 다루는 문서가 있는지 확인한다
- 기존 문서와 모순되는 내용이 없는지 확인한다
- 중복이 있으면 한 곳으로 통합하고 나머지는 참조로 대체한다

## 8. 참조 링크 및 파일 경로 검토

문서 내 모든 참조가 유효한지 확인한다.
- 파일 경로가 실제 존재하는 파일을 가리키는지 확인한다
- 외부 URL이 유효한지 확인한다
- "위 문서 참고" 같은 표현 대신 파일 경로를 명시했는지 확인한다

## 9. 전체 변경 사항 재검토

모든 변경 파일을 처음부터 다시 검토한다.
- diff를 전체적으로 훑는다
- 불필요한 변경이 섞이지 않았는지 확인한다

## 10. 불필요해진 문서 정리

변경으로 인해 더 이상 필요 없는 문서를 제거한다.
- 통합된 문서의 원본을 삭제한다
- 빈 파일이나 빈 디렉토리를 정리한다
- 다른 문서에서 삭제된 문서를 참조하고 있지 않은지 확인한다

## 11. 최종 품질 검토

문서가 프로젝트 기준에 부합하는지 확인한다.
- 맞춤법과 문법을 확인한다
- 파일명이 소문자와 하이픈 규칙을 따르는지 확인한다
- frontmatter가 6줄 이내인지 확인한다

## 12. 독자 흐름에서 문제가 없는지 확인

실제 독자 입장에서 문서를 검증한다.
- 문서 진입점(guide.md)에서 원하는 정보까지 도달할 수 있는지 확인한다
- 사전 지식 없이 따라갈 수 있는지 확인한다

## 13. 배포 가능 퀄리티인지 검토

공개해도 되는 수준인지 최종 판단한다.
- 민감한 정보(내부 URL, 비밀번호 등)가 포함되지 않았는지 확인한다
- 모든 placeholder가 실제 내용으로 치환되었는지 확인한다
- 긍정적인 입장과 부정적인 입장 둘이서 토론하면서 검증한다. 최대 3번만 주고받는다

## 14. 커밋 및 PR 작성

변경 사항을 커밋하고 PR을 생성한다.
- 커밋 메시지를 컨벤션에 맞게 작성한다
- PR은 항상 develop 브랜치를 대상으로 생성한다
- .github/ 에 PR 템플릿이 있으면 이를 활용한다. 없으면 자유롭게 작성한다
- PR 설명에 변경된 문서 목록과 변경 목적을 기술한다
- 리뷰어를 지정한다

## Branch Strategy

main          - production
develop       - 통합
docs/*        - 문서 작성/수정

## Commit Convention

type: subject

type: docs, fix, chore

예시:
- docs: API 레퍼런스 문서 추가
- fix: getting-started 가이드 오류 수정
```
